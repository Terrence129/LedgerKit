# ADR-0003：类型化业务事件、确定性分录与可重建投影

> 状态：Accepted
>
> 日期：2026-09-02
>
> 决策者：项目所有者
>
> 授权：项目所有者在 M0 实现提示中明确接受本决策方向，并授权本 ADR 直接设为 Accepted。
>
> 关联规则/里程碑：M0、EVT-001 至 EVT-005

## 背景

复制 Excel 的多表公式会让现金、持仓、报表和导入器各自形成业务逻辑；直接建设企业级复式会计平台又会扩大 1.0 的概念和维护成本。LedgerKit 需要一套可解释、可审计且能够确定性重放的内核。

## 决策驱动因素

- 财务规则只有一个权威实现
- 每个汇总结果可追溯到业务意图和确定性影响
- 投影损坏或算法升级后可重建
- UI 与导入器不能绕过领域不变量

## 方案

### 方案 A：类型化业务事件、轻量分录和投影

类型化 `BusinessEvent + Detail`、主数据和市场数据修订是源事实；Core 从事件确定性生成 `LedgerPosting`；余额、持仓、支出和估值是带版本与水位的派生查询或投影。

### 方案 B：直接更新余额和报表表

查询简单，但业务意图、计算过程和历史版本丢失，无法可靠重建或解释迁移差异。

### 方案 C：通用复式会计输入接口

审计表达能力强，但用户和 UI 需要理解账户科目与借贷，并可能允许任意 posting 绕过产品业务规则。

## 决策

接受方案 A：

- `BusinessEvent` 及其唯一类型明细、主数据和不可变市场数据修订构成源事实。高层命令表达收入、支出、调拨、换汇、买卖、股息、投资费用、期初和更正。
- `LedgerPosting` 只能由 Domain/Core 从规范化事件和明确的计算版本生成。外部不能独立创建、修改或删除 posting。
- 同一规范事件流按 `(effective_date, sequence, event_id)` 和相同计算版本重放，必须产生相同的 posting 规范序列与 SHA-256。
- 业务事件、明细、FX resolution、posting、审计记录和投影水位更新在同一个 SQLite transaction 中提交。
- 余额、持仓、净资产、质量检查和可选物化汇总是可删除并重建的派生数据。投影记录 `calculation_version` 和最后事件水位；版本或水位不匹配时不得展示混合结果。
- 支出分析首版是同一 SQLite read snapshot 上的具名只读查询，不默认建立另一套持久化事实。若性能门禁失败，只能以新 ADR 增加可重建物化层。
- Domain 不依赖 UI、SQLite、Tauri、Avalonia 或 XLSX 库；适配器只做持久化、平台和格式转换。

## 后果

- 正面影响：业务意图、派生影响和查询状态可追溯；候选技术栈共享同一 fixture 契约。
- 负面影响：需要事件明细、posting 生成器、重放器和水位管理，早期实现量高于直接 CRUD。
- 数据迁移影响：导入器先生成规范事件，再由 Core 生成 posting；不能导入 Excel 派生余额作为事实。
- 测试与运维影响：每类事件都要验证正常、边界、失败、事务回滚、规范序列和投影重建哈希。

## 反转条件

若 1.0 之外需要完整会计科目、外部凭证互操作或法规级双重记账，可在保留业务事件作为命令来源的前提下通过新 ADR 扩展 posting 模型。不得以性能优化为由把派生表升级为不可重建事实。

## 验证

- 脱敏 fixture：`fixtures/sanitized/01-cny-income-expense/` 至 `fixtures/sanitized/31-expense-excel-difference-bridge/`
- 自动化测试：所有 fixture 的事件、posting、投影和错误结果由两种候选栈共同消费
- 性能/体积/恢复验证：10 万事件重建与查询门禁在后续里程碑执行
- 对账或差异桥：posting/projection canonical hash 和 Excel 双口径桥
