# ADR-0010：P0 手动更新、P1 签名与自动更新

> 状态：Accepted
>
> 日期：2026-09-02
>
> 决策者：项目所有者
>
> 授权：任务 04 要求固定 P0 不自动联网更新、P1 再引入签名/自动更新，并明确 Beta 未签名。
>
> 关联规则/里程碑：M1、M6、ADR-0001

## 背景

P0 核心必须默认零网络；当前没有代码签名证书，也没有安全更新源、签名 key 生命周期、回滚和发布运维证据。把自动更新塞入 Beta 会增加网络、供应链和权限面，并可能让未签名 artifact 被误解为正式可信发行物。

## 决策驱动因素

- 默认运行时网络请求为零
- 安装 artifact 的来源、完整性和发布者身份可解释
- Beta 范围、依赖与运维面最小
- P1 能在完整威胁模型下增加签名更新

## 方案

### 方案 A：P0 自动更新

需要更新插件、网络 endpoint、manifest/artifact 签名、密钥和故障恢复，当前证据不足。

### 方案 B：P0 手动更新，P1 再签名与自动更新

应用不检查更新、不联网下载。Beta artifact 明确未签名；用户从项目公开渠道手动获取并安装。

## 决策

接受方案 B：

- P0 和 `1.0.0-beta.1` 不包含 updater 插件、后台检查、启动检查、更新 endpoint 或隐式网络请求。
- Beta NSIS 明确标记“未签名测试版本”；不得声称 Windows 发布者身份已验证。没有用户另行授权，不创建 GitHub Release。
- P0 更新由用户明确离开应用后手动下载/安装；升级前必须创建并验证一致性备份，并通过 schema 前向 migration 与失败保留旧库流程。
- 代码签名、artifact 签名、更新 manifest、HTTPS 获取、回滚与 key rotation 留到 P1。启用前必须有新的 Accepted ADR、生产证书、签名验证 E2E、断网/篡改/回滚测试和可撤销发布流程。
- WebView2 自身由 Windows/Microsoft Evergreen servicing 更新，不属于 LedgerKit 应用自动更新；每次 runtime 变化仍触发 ADR-0009 的兼容性门禁。

## 后果

- 正面影响：P0 默认网络面与依赖最小，不会伪装未完成的签名基础设施。
- 负面影响：用户需要手动检查并安装新版本；未签名 Beta 会触发 Windows 警告，不适合作为广泛正式发行。
- 数据迁移影响：手动升级仍必须执行受控备份、migration、验证和失败回滚。
- 测试与运维影响：Beta 记录未签名；P1 自动更新不得复用本 ADR 假设直接上线。

## 反转条件

当生产证书、签名密钥运维、可信更新源、用户同意模式和端到端升级/回滚证据全部就绪时，以新 ADR 接受 P1 自动更新。发现紧急安全漏洞不会授权应用绕过用户自动联网；应通过公开渠道发布手动安全更新。

## 验证

- 脱敏 fixture：不适用
- 自动化测试：依赖/源码扫描确保无 updater 和网络 client
- 性能/体积/恢复验证：M1 默认远程 endpoint 为零；M6 手动升级恢复演练
- 对账或差异桥：升级前后账本 canonical hash
